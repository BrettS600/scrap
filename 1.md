# scrap

Page watching and text collection built on [Scrapling](https://scrapling.readthedocs.io/). `4.py` runs from your own computer on your home internet (a residential IP, so no proxy) and checks one page about every 90 seconds; to the site, that looks like a person refreshing. `8.py` and `6.py` work through a big list of links using a Decodo residential proxy, on your Mac. `9.py` and `10.yml` do the same on GitHub's computers, starting by themselves whenever links are added.

| File | What it is |
|---|---|
| `1.md` | This guide |
| `2.txt` | The Python package list (Scrapling 0.5 with its browser fetchers, and openpyxl for reading your spreadsheet) |
| `3.py` | One-time setup: installs Scrapling and its browser, and checks for Google Chrome |
| `4.py` | The watcher: checks a page every ~90 s, reports new listings or changes, and works around blocks by itself |
| `5.py` | API finder: opens the page once and lists the background JSON calls it makes |
| `6.py` | Gets the text of every link in your spreadsheet through your Decodo proxy, and picks up where it left off |
| `7/` | Handoff notes: what was built, research findings, current status and next steps. Start with `7/1.md` when picking this up in a new chat or with another AI. |
| `8.py` | Opens every link in your private `links.csv` through your Decodo proxy and collects only the text you choose. Nothing private leaves your Mac. |
| `9.py` | The automatic queue: does what `8.py` does, but on GitHub's computers, starting by itself whenever links are added. Run by `10.yml`. |
| `10.yml` | The GitHub workflow for the automatic queue. Copy it into your results repo (see below); it doesn't run in this repo. |
| `11.py` | **The link opener for your extension:** it opens each link with your extension loaded and saves the extension's reads to your inbox repo. GitHub runs it for your barcode scans (through `12.yml`), and `13.py` runs it on your Mac for the big list. |
| `12.yml` | The GitHub workflow for the link opener: your barcode-scan list (`scans.csv`), through Decodo. Copy it into your results repo (see "Opening links for your extension" below). |
| `13.py` | **Your big list on your Mac:** runs the link opener over your home internet, with no proxy, so it costs nothing. See "Your big list on your Mac" below. |

## Setup (once)

1. Open this folder in VS Code and pick a Python 3.10 or newer interpreter (Cmd+Shift+P → *Python: Select Interpreter*).
2. Open `3.py` and press **Run**. Wait for `Setup done.`

## Watching a page (`4.py`)

At the top of `4.py`:

- `URL` is the page to watch. A search-results page sorted by newest is ideal. Or leave `URL` blank and use your spreadsheet:
  - `LINKS_FILE` is the full path to your .xlsx. In Finder, right-click the file, hold **Option**, choose **Copy "…" as Pathname**, and paste it between the quotes. Keep the spreadsheet outside this folder, so it can't end up on GitHub.
  - `LINK_ROW` is the row to use (3 to start). The watcher takes the black-highlighted link in that row, or the row's only link, and never shows its address.
- `HIDE_ADDRESS = True` replaces the page's address and the site's name everywhere: the output, Scrapling's own log lines, `4-checks.csv` and `4-blocks.csv`. You can paste those to someone for help without showing them the link.
- `HEADLESS = False` (the default) opens a Chrome window so you can watch it work. It's your Google Chrome app, but with a separate, clean profile: none of your logins, bookmarks or tabs. Set `True` to run it hidden.
- `ITEM_SELECTOR` is optional but recommended. It's a CSS selector for one listing on that page, such as `li.result`, and with it set the watcher reports each new listing (its text, link and `PRICE_SELECTOR` price). Left blank, it only reports that the page's text changed, which on busy pages can mean every check.
- `WAIT_SELECTOR` is optional. It makes the watcher wait until the listings have loaded, which helps on JavaScript-heavy sites. Setting it to the same value as `ITEM_SELECTOR` usually works.

Press **Run**. The first check records what's already on the page; after that, only new listings print as `NEW: …`. Stop it with the stop button. Your cookies are saved, so the next run skips the Cloudflare check if the clearance is still valid.

### Stealth settings it uses

These are all Scrapling options:

- your real Google Chrome (`REAL_CHROME`)
- automatic Cloudflare Turnstile and "Just a moment" solving
- canvas noise
- WebRTC leak blocking
- a real user agent for that browser
- one browser session kept open, so the fingerprint and cookies stay the same between checks
- a randomized gap between checks (70–110 s to start; it adjusts this itself, see below)

The timezone and language come from your computer, which matches your home IP.

### When it gets blocked

It works out what kind of block it hit and tries the fixes for that kind, one per blocked check. Before each retry it waits twice as long as the last time, up to 30 minutes.

| Kind of block | What it tries, in order |
|---|---|
| Rate limit (HTTP 429, Cloudflare 1015) | Wait as long as the site's `Retry-After` header asks, then check 1.5× slower |
| Challenge it couldn't pass ("Just a moment" stays) | Wait → visible Chrome window → fresh session → slow down |
| Browser-fingerprint ban (Cloudflare 1010) | Fresh session → visible Chrome → switch to the bundled Chromium |
| Firewall block (403, Cloudflare 1020, "Sorry, you have been blocked") | Fresh session → visible Chrome → slow down |
| Quiet block (page loads but the listings and links are missing) | Fresh session → visible Chrome → slow down |
| IP ban (Cloudflare 1006–1008) | Nothing on your computer can fix this, so it goes straight to sleeping |

A fresh session wipes the cookies and opens a new browser, which gets a new fingerprint. A lost internet connection isn't treated as a block: it just retries every minute.

**When it runs out of fixes**, it stops checking and goes quiet for 3 hours, then makes one test check. If that check is still blocked, it sleeps 6, then 12, then 24 hours before each later try. Once a test check passes, it goes back to watching 1.5× slower than before. It never quits on its own.

**What it learns** (saved per site in `data/4-learned.json`):
- **The fastest safe speed.** After 6 hours without a block, it tries checking about 10% faster. If that gets blocked within 2 hours, it goes back to the old speed and never goes that fast on that site again. It never goes below `FASTEST_SECONDS` (60 s).
- **Which browser setup works.** If the visible window or the other browser fixed a block, it keeps using that.
- **Where the listings are after a redesign.** It uses Scrapling's adaptive matching to find the listings by their old look and switches to the new selector. If the site is rebuilt too much to follow, it says so and asks you to update `ITEM_SELECTOR`.

On each start it prints what it has learned. If you change a setting at the top of `4.py`, your new value replaces what it learned for that setting. `RESET_LEARNING = True` makes it forget everything for that site.

It never rewrites its own code or upgrades Scrapling. Once a day it checks whether a newer Scrapling is out and prints a note if so.

If it keeps sleeping on a site, your options are to wait, poll the site's API instead (see `5.py`), use a proxy for that site, or check less often.

## Getting the text of every link (`6.py`)

`6.py` goes through your spreadsheet row by row, gets each page's text through your Decodo residential proxy, and saves it.

**How it gets past Cloudflare cheaply.** A browser opens the first page from a site and passes Cloudflare's check; that's the slow part, up to about 45 seconds. The proxy keeps the same IP for a while (a "sticky" session), so every other page from that site is fetched as plain text with that same pass and IP: no browser and no images, so it's fast and uses very little data. If the site asks again, it goes back to the browser. If plain text never works on a site, it uses the browser for that site, skipping images and fonts to save data. If an IP gets blocked, that browser moves to another proxy port, which means another IP.

**One-time setup**

1. In Decodo, go to Residential → Proxy setup. Set Location to the country the site serves and Session type to Sticky (30 min if offered).
2. Save your proxy password on your Mac and nowhere else. In VS Code, go to File → New Text File, paste only the password, then Save As in your home folder (the house icon) as `decodo-password.txt`.
3. At the top of `6.py`, set:
   - `LINKS_FILE`: the same spreadsheet path as in `4.py`.
   - `PROXY_HOST`, `PROXY_PORTS` and `PROXY_USER`: copy these from the table in Proxy setup (address, the range of ports, username).
   - `TIMEZONE`: only if the proxy's country isn't the one you're in.

**Running it**

- `LIMIT = 50` does 50 lookups and stops. Keep it small while you're on the 100 MB trial, then check Decodo's **Usage statistics** to see how much data they used. Set `LIMIT = 0` to do the whole list.
- `BROWSERS` is how many work at once, each on its own IP. More is faster.
- Stop it any time. Run it again and it carries on from where it stopped. A row that fails 3 times is left alone.
- The output only ever shows row numbers, never addresses or your password, so it's safe to share.

## Collecting chosen text from your links (`8.py`)

`8.py` keeps the links, the pages and the results in one private folder on your Mac, `scrap-private` in your home folder. Nobody who only sees this repo or the terminal output learns any of them. Another chat that you allow to see that folder decides which text to collect.

1. **Set up the folder.** Make `scrap-private` in your home folder (Finder: Go → Home, File → New Folder). Put your CSV in it and name it `links.csv`. By default it uses the first web address in each row; `LINK_COLUMN` can pick a column by number or heading instead.
2. **Sample run.** Press Run on `8.py`. It opens the first 20 links through the proxy and saves those pages, complete, into `scrap-private/samples`. It also writes `HOW-TO-fields.md`, then stops.
3. **The other chat picks what to collect.** Open an incognito chat and give it `scrap-private`, either with Add folder in the Claude desktop app or by uploading the files. Ask it to read `HOW-TO-fields.md` and the samples, then write `fields.json` for the text you want.
4. **Full run.** Press Run again. It opens every link that isn't done yet, pulls out those items and saves them to `scrap-private/results.csv`, one row per link. `LIMIT` caps each run (50 to start, for the trial); set `LIMIT = 0` for everything.
5. **New links** added to `links.csv` are picked up on the next run. Set `WATCH_MINUTES` (say 30) and it keeps running, checking for new links that often.
6. **Storing the results.** The other chat reads `results.csv` and stores the data in your repo. Use any repo except this one.

How it works:

- **Cloudflare:** like `6.py`, a browser passes Cloudflare once per proxy IP, then pages come as plain text over the same IP. If an item only appears after the page's JavaScript runs, it reopens the page in the browser, and after 3 such pages it uses the browser for that site.
- **Time zones:** each browser's clock is set to wherever its proxy IP is, because Cloudflare checks for a mismatch.
- **Privacy:** the terminal only ever shows row numbers and counts, like "Row 412: ok - 5 of 5 items."

Keep `scrap-private` out of this repo, and don't give it to a chat that shouldn't see your links.

## The automatic queue on GitHub (`9.py` and `10.yml`)

This does the same job as `8.py`, but on GitHub's computers, so it keeps going with your laptop off and starts by itself when links are added. It works in your results repo, `results-links`; this repo only holds the code.

- **Queue 1 (open):** opens each new link through Decodo and saves the page.
- **Queue 2 (read):** reads the saved pages, pulls out the items in `fields.json`, and saves them in `results.csv`, one row per link.

The saved pages are kept with each run for 30 days, outside the repo. When `fields.json` changes, every saved page is read again without reopening any links.

**Setup (once, on GitHub, in the results repo)**

1. **Add the proxy password as a secret.** Go to Settings → Secrets and variables → Actions → **New repository secret**. Set Name to `DECODO_PASSWORD`, paste the password from your `decodo-password.txt` into Secret, then press **Add secret**. GitHub keeps it hidden: it never shows in the logs, and nobody can read it back, you included.
2. **Add the workflow.** Go to **Add file → Create new file**, type the name `.github/workflows/10.yml`, paste in everything from `10.yml` in this repo, and press **Commit changes**. The first run starts by itself.

**What happens next**

1. **First run:** there's no `fields.json` yet, so it opens the first 20 links and saves them in `samples/`, along with `samples/HOW-TO-fields.md`.
2. **The other chat** reads the samples and writes `fields.json` in the top folder of the results repo. That starts a run.
3. **From then on,** new links go into `results.csv` by themselves.

A run starts when the links file, `fields.json` or `10.yml` changes, every 6 hours to pick up anything left over, or when you press **Actions → Link queue → Run workflow**. Only one run goes at a time.

**Settings** are at the top of `10.yml` in the results repo. To change one, open the file there and click the pencil icon.

| Setting | What it does |
|---|---|
| `LIMIT` | The most links one run opens (50 to start, for the trial). `0` = no limit. |
| `KEEP_GOING` | `"true"` starts the next run straight away while links are left. With `"false"`, the rest wait for the 6-hourly run. For the big backlog, set `LIMIT: "0"` and `KEEP_GOING: "true"`. |
| `BROWSERS` | How many browsers work at once, each on its own proxy IP. |
| `MAX_FIELD_CHARS` | The longest text kept per item. It keeps `results.csv` under GitHub's 100 MB limit for a single file. If the results ever pass 95 MB, they carry on in `results-2.csv`. |

**Buttons:** Run workflow on the Actions tab has three tick boxes:
- *Read every saved page again*: use it after fixing `fields.json`. Changing `fields.json` already does this by itself.
- *Try links that already failed 3 times again.*
- *Open pages again that came out with missing items*: needed when a new item only appears once the page's JavaScript runs.

**Files in the results repo**

| File | What it is |
|---|---|
| your links `.csv` | Your links. Add more any time. If there's more than one CSV, it uses `links.csv`, or set `LINKS_FILE`. |
| `fields.json` | What to collect (the other chat writes it) |
| `results.csv` | One row per link: row number, link, status (ok, not found, or the kind of block), one column per item, then `found` (like `4 of 5`), how it was opened, tries, time (UTC) and run number |
| `samples/` | The first pages, `HOW-TO-fields.md`, and `index.csv` listing which link each sample came from |
| `check/` | Up to 20 recent pages where some items came out empty, for fixing `fields.json`. It empties itself once those rows are complete. |

**Watching it:** the Actions tab lists every run. Click one to see its summary or log. The logs only show row numbers and counts. Because the results repo is public, anyone can see its results, samples, logs and saved pages.

**Things to know:**
- **The proxy check:** each run tests the proxy password first. If Decodo turns it down, the run stops before touching any links and says so.
- **Cloudflare on GitHub:** GitHub's computers run Linux, which Cloudflare may treat differently from your Mac. The sample run shows whether it gets through.
- **Cost on GitHub:** GitHub Actions is free on public repos. Decodo's data use is the cost; see its Usage statistics.

## Opening links for your extension (`11.py` and `12.yml`)

This replaces the queue above. Your Chrome extension already reads each page and saves it, so all GitHub needs to do is open the links: with your laptop off, and through your proxy. It works in your results repo, `results-links`.

**Two lists, two setups (since 2 Nov 2026):** GitHub does your barcode scans, a few hundred links in `scans.csv`, through Decodo. Your big list, `links.csv`, is done on your Mac by `13.py` (next section), because it's free there and because GitHub's rules say its free computers shouldn't be used for long jobs unrelated to the repo's code. `LINKS_FILE: "scans.csv"` in `12.yml` keeps GitHub off the big list.

For each link in the scan list that isn't done yet, a run:
1. opens the page through Decodo, in a browser with your extension loaded (one page at a time per browser, never hundreds of tabs);
2. waits until Cloudflare's check has passed and your extension has read the page;
3. saves the extension's reads to your inbox repo, in exactly the file format your extension uses, 100 reads per save. Each save is one git push, so GitHub's limit of about 500 API saves an hour doesn't apply.

The extension gets no key on GitHub, so it never sends anything by itself and nothing is saved twice. A link only counts as done once its read is saved.

**Setup (once, on GitHub, in the results repo)**

1. **The scan list:** `scans.csv` in the top folder, one link per row (full `https://` addresses). Add rows any time; each change starts a run. Until it exists, runs have nothing to do.
2. **The extension:** upload your extension's whole folder as `cert-reader/` (Add file → Upload files, drag the folder in). It's public there like everything else in that repo, so make sure there's no key or saved data in it.
3. **Two secrets** (Settings → Secrets and variables → Actions → New repository secret):
   - `DECODO_PASSWORD`: your proxy password (`pbcopy < ~/decodo-password.txt` in Terminal copies it without showing it).
   - `CARD_INBOX_KEY`: a GitHub key that can write to the inbox repo (fine-grained token, only that repo, Contents: Read and write).
4. **The workflow:** Add file → Create new file, name it `.github/workflows/12.yml`, paste in everything from `12.yml` in this repo, Commit changes. The first run starts by itself.

**When it runs:** when `scans.csv` or `12.yml` changes, every 6 hours to pick up anything left over, or when you press **Actions → Link opener → Run workflow**. One run at a time.

**Settings** (top of `12.yml` in the results repo; edit with the pencil icon):

| Setting | What it does |
|---|---|
| `LINKS_FILE` | Which list GitHub opens: `scans.csv`, your barcode scans. |
| `LIMIT` | The most links one run opens (50 to start). `0` = no limit. |
| `KEEP_GOING` | `"true"` starts the next run straight away while links are left. |
| `BROWSERS` | How many browsers work at once, each on its own proxy IP. |
| `READ_WAIT_SECONDS`, `SETTLE_SECONDS` | How long to wait for the extension's first read of a page (25 s), and how long a read must stay unchanged to count as finished (5 s; covers parts of a page that load late). |
| `LIGHT` | Saves proxy data: after the first page on each proxy address, pages skip pictures, fonts, video and ad/tracking scripts, while the browser's cache keeps the site's own code from downloading again. If a page then gives no read, it's opened again in full, and after 3 of those the run loads every page in full. |
| `BATCH` | Reads per save (100). The first save of each run comes after 5 reads, so a bad key shows up early. |

**`opened.csv`** (written by the runs, in the results repo): one row per link with its status: `saved`, `not found`, `no read` (the extension didn't read the page), the kind of block, or `error`, plus tries and time. A link that fails 3 times is left alone; the **Try links that already failed 3 times again** box on Run workflow tries them again.

**Watching it:** each run's summary on the Actions tab shows how many links were read and saved, and roughly how much proxy data each page used, so you can work out the cost before Decodo's dashboard catches up. The logs only show row numbers and counts.

**If something's wrong, the run stops before touching any links and says what to fix:** a missing secret, Decodo turning down the password (or the plan being out of data), the inbox key being wrong or expired, or the extension folder missing.

## Your big list on your Mac (`13.py`)

`13.py` runs the same link opener on your Mac, over your home internet, with no proxy, so it costs nothing. A browser window with your extension loaded opens each link in `links.csv`, waits for Cloudflare's check and your extension's read, and saves the reads to your inbox repo, 100 at a time, exactly like GitHub does.

**Setup (once)**

1. **Keep GitHub off the big list.** In `results-links`, open `.github/workflows/12.yml`, click the pencil, and change the `LINKS_FILE` line to
   `  LINKS_FILE: "scans.csv"`
   (two spaces in, like the lines around it). Commit changes.
2. **A key for your inbox**, saved on your Mac (this Mac's version of the `CARD_INBOX_KEY` secret):
   - On GitHub: your picture → **Settings** → **Developer settings** → **Personal access tokens** → **Fine-grained tokens** → **Generate new token**. Name it "Mac inbox"; pick an expiry date after you expect the big list to finish; **Only select repositories** → your inbox repo; **Repository permissions** → **Contents: Read and write**. Generate it, but don't copy it yet.
   - In Terminal, type this and **don't press Enter yet**: `pbpaste > ~/card-inbox-key.txt && chmod 600 ~/card-inbox-key.txt`
   - Now copy the key on GitHub, go back to Terminal and press Enter. (Doing it in this order stops the command itself from replacing the key on the clipboard.)
3. **Get `13.py`** into your scrap folder, next to `3.py`. You only need `13.py`: each time it starts, it gets the latest `11.py` from GitHub by itself.
4. `3.py` must have been run once (it installs Scrapling and its browser). You did this on 30 Oct.

**The first run: a test of 50 links**

1. Plug the Mac in. Open `13.py` in VS Code and press **Run**.
   - If a box pops up offering to install the "command line developer tools" (that's git, which saves the reads), click **Install**, wait for it to finish, then press Run again.
2. A browser window opens and works through the links. Leave it alone; you can watch, and use the Mac for other things.
3. When it says **Test done**, copy the last lines of the terminal into the chat. They only show row numbers and counts.

**The big run.** If the test looks fine, set `LINKS_PER_START = 0` at the top of `13.py` and press Run. It keeps going until every link is done:
- **Keep the Mac plugged in with the lid open.** It won't sleep while this runs, and the screen stays on.
- **Stop it any time** by clicking in the terminal and pressing **Ctrl+C**: it finishes the page it's on and saves. Press Run again later and it carries on from there. Closing VS Code or the terminal also stops it; nothing is lost, the last few links just get opened again.
- **If the internet drops,** it waits 10 minutes and carries on.
- **If the site starts blocking,** it pauses, then waits 2 hours and tries again. After 3 blocked tries in a row it stops and says so. A block lands on your home internet, so the site may not load in your own browser for a while; it's usually temporary.
- **New links** added to `links.csv` are picked up each time it starts again.

**Settings** (top of `13.py`):

| Setting | What it does |
|---|---|
| `LINKS_PER_START` | `50` for the first test, then it stops. `0` = the whole list. |
| `BROWSERS` | Browser windows at once (1). They all share your one home address, so more windows means more visits per hour from it, and a higher chance of blocks. |
| `PAUSE_SECONDS` | Wait between pages (3–8 s, picked at random). Longer is gentler on the site, but slower. |
| `RETRY_FAILED` | `True` also tries links that already failed 3 times. |
| `WAIT_AFTER_ERRORS_MINUTES`, `WAIT_AFTER_BLOCKS_MINUTES` | How long it waits after the internet drops (10) or after blocks (120) before carrying on. |

**Where things are on your Mac** (in `scrap-private`, in your home folder):
- `results-links/`: its copy of your results repo (the links list and the extension). It's refreshed each time it starts, so don't keep anything else in it.
- `mac-progress.csv`: one row per link with its status, like `opened.csv` on GitHub. The first run counts the links GitHub already finished as done.
- `mac-log.txt`: everything the terminal showed (row numbers and counts only).
- `mac-work/`: the browser's profile and a copy of the code.

**How fast:** with 1 browser it does very roughly 200–250 links an hour, so the whole list takes a few weeks of running. Cloudflare decides the safe pace, not the Mac.

## Finding the site's API (`5.py`)

Set `URL` and press **Run**. It loads the page, scrolls, and prints the background calls, JSON first. If the listings come from one of them, polling that endpoint costs kilobytes instead of a full page load, and it can be checked more often.

## The `data/` folder

The scripts create it next to themselves:

| File | Contents |
|---|---|
| `4-checks.csv` | One row per check: time, result (ok or the kind of block), status, items, new items, current speed and browser setup |
| `4-blocks.csv` | Every block: what kind it was, and what it did about it |
| `4-items.csv` | Every new listing, with the time it was first seen |
| `4-learned.json` | What it has learned for each site |
| `4-seen.json` | Listings already seen, so a restart doesn't re-alert |
| `4-adaptive.db` | The "look" of the listings, used to find them again after a redesign |
| `4-browser-state.json` | Your browser cookies. Keep this private. |
| `5-api-calls.json` | What `5.py` found |
| `6-text.csv` | `6.py`'s results: one row per spreadsheet row, with its status, whether it came as plain text or through the browser, the page title and the page text (cut at 32,000 characters, Excel's limit per cell) |
| `6-text.db` | The same results, used to carry on where it left off. Don't delete it in the middle of a job. |

Don't commit the `data/` folder. It holds your cookies.

With `HIDE_ADDRESS` on, `4-checks.csv`, `4-blocks.csv` and the output in the terminal are safe to share. The other files contain the real address or the listings' real links, so keep them to yourself.
