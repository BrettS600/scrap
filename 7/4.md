# Timeline of the first session (29–30 October 2026)

1. **Checklist vs. Scrapling.** The owner shared Gemini's answer on what scraping behind Cloudflare needs: a stealth browser, TLS and header matching, challenge solvers, residential proxies, keeping the `cf_clearance` cookie, fingerprinting, behaviour and network leaks. We checked it against Scrapling's docs. Summary: Scrapling covers almost everything except the proxies themselves, human-like mouse and typing, random timing and a few fingerprint surfaces. Details are in `7/2.md`.
2. **Proxy basics.** We covered what a proxy does (it changes the IP the site sees), rotating vs sticky, residential vs datacenter, rough prices, and what 1,000 requests a day means (one every ~90 s). We agreed to **start on the home IP** at about one request every 90 s.
3. **Repo created.** A private `BrettS600/scrap` repo, with every file named by a number: `1.md`, `2.txt`, `3.py`, `4.py`, `5.py`. GitHub's empty README was removed to keep the naming rule. The owner asked that no other repositories be looked at, and none were opened.
4. **Self-fixing watcher.** The owner asked whether it could learn from blocks and update itself. We added block classification, a fix list for each kind, sleeping when out of fixes and per-site learning to `4.py`. Phone alerts were offered and declined. The script deliberately never rewrites its own code or upgrades Scrapling.
5. **Private links.** The owner shared a spreadsheet with their links highlighted in black, so they wouldn't be seen. The spreadsheet was **not opened** and **not added to the repo**: black fill only hides text visually, and the GitHub tool can't upload binary files. Instead `4.py` reads the link itself from a path on the Mac and hides it everywhere. It opens a visible Chrome window, and the owner presses Run, because any screen-viewing tool would have shown the address bar.
6. **First real run.** It worked on the owner's Mac. The owner meant row 3, not row 2, so the default became `LINK_ROW = 3`, and that worked too, with about 45 s on the first load. We confirmed it reuses one window and doesn't keep opening new ones.
7. **Proxy research** for ~115,000–130,000 lookups on Cloudflare. The owner only needs page text. Recommendation: **Decodo**, test small first, keep each IP sticky and fetch the text plainly after the browser passes Cloudflare. Estimated ~4–40 GB in total if plain text works. Details are in `7/2.md`.
8. **Proxidize mix-up.** Searching for Decodo led to Proxidize's site, a different company. The owner went to decodo.com directly, started the **100 MB free trial** instead of a 25 GB monthly plan, and set up Proxy setup: USA, Sticky 30 min, `us.decodo.com:10001–10010`, user `user-sp2e2o4qkx-sessionduration-30`.
9. **`6.py` built** for the batch: plain text after a browser pass, a fallback to the browser, moving off blocked IPs, resuming, and only row numbers in the output. It was tested against a fake site and proxy and pushed. It hasn't run for real yet.
10. **Password saved** to `~/decodo-password.txt` with `pbpaste`. The first attempt saved the command instead of the password and the proxy answered 407; it was fixed by copying the password last. **Proxy verified:** a US residential exit IP (Spectrum, Michigan).
11. **Handoff notes** (this folder) added at the owner's request.
12. **The privacy model.** The owner wanted "the AI opens the links but never sees the links, the pages or the data, and a second chat reads the pages and records the data in a repo." Options weighed:
    - uploading the CSV here, or into this repo: no, because the AI would see every link;
    - showing the AI the links but asking it "not to reason" about them: no, because recognition can't be switched off, and the AI's workspace can't reach outside websites anyway.

    Agreed instead: the links CSV stays in `~/scrap-private` on the Mac, code built here opens the links on the Mac, and a second incognito chat sees the pages, writes the rules for what to collect, and stores the results somewhere other than this repo.
13. **`8.py` built** for that: sample run, then `fields.json` from the second chat, then the full run into `results.csv`, plus per-IP time zones and pickup of new links. Tested against a fake site and proxy and pushed. `6.py` got the `us.decodo.com` settings.

**Still open:** the owner's first sample run and full run with `8.py`, measuring data use, and the trial decision before about 2 Nov 2026. See `7/1.md`.

## Second session (31 October 2026)

14. **The GitHub idea.** The owner wants it all on GitHub so it runs with the laptop off. Adding a link should queue its page to be opened, an opened page should queue the text to be read, and everything should land in one links file and one results file. Later, a phone barcode scan could add a link. Designed as two queues on GitHub Actions in a separate repo. The pages are handed over as saved files, not screenshots, because a screenshot would need OCR or an AI to read back.
15. **Results repo created.** `BrettS600/results-links`, created empty, because a "/" isn't allowed in repo names. The builder chat promised never to open it again. The owner then made it and `scrap` **public**, saying the data ends up on a password-protected site anyway. They were told:
    - the site's password doesn't protect a public repo;
    - all of `scrap`'s commits show their Gmail address, and turning on GitHub's email privacy setting keeps it off future commits.

    The owner uploaded the links CSV to `results-links` themselves.
16. **Built `9.py` + `10.yml`.** This is the queue described in `7/3.md`, tested end to end on fakes. The owner still has to add the secret and copy the workflow into `results-links`.
