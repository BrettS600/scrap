# Third session (2 November 2026): opening links for the owner's extension

## What changed and why

The owner has their own Chrome extension that reads each page and saves it to GitHub. Opening one of their links in Chrome is all it takes. So the job is no longer "read the pages": it's just **open every link, with the extension loaded, behind Cloudflare, with the laptop off.** The reading step built on 31 Oct (`9.py` queue 2, `fields.json`, samples, the second chat writing rules) is no longer needed. `9.py` + `10.yml` stay in the repo but are replaced by `11.py` + `12.yml`.

The owner shares facts about the extension and their other repos only through their other chat, with private parts blanked out ("confidential"). Never open those repos or the extension's code (rule 6a in `7/1.md`). When information is needed, write a question for the owner to pass on, worded so it doesn't reveal what this repo does. The owner explicitly didn't want the other chat to know about the link opener.

## What's known about the extension (from the other chat)

- **Manifest and loading:** Manifest V3, no `"key"` field, plain JavaScript, loads unpacked as-is. The owner will upload it to `results-links` as `cert-reader/`.
- **Key and settings:**
  - The key is entered in the popup (`popup.html`) and stored in `chrome.storage.local` as `ghKey`.
  - `autoSave` (default on) rewrites a `results.csv` in the Downloads folder.
  - Other storage names: `records` (every read, keyed `<GRADER>:<cert>`), `outbox` (`{key: true}` until sent), `last`, `lastSave`, `ghStatus`.
- **Reading:** the content script runs at `document_idle`. It reads 1.5 s later, and again 1.2 s after the page stops changing, which catches a table that loads late. It doesn't need images or styles.
- **Sending:** about 2.5 s after the last read, one GitHub Contents API PUT per read. The file is `certs/<grader lowercase>_<cert>_<ms>.json` in the inbox repo, holding the record as compact JSON. The extension also sends on Chrome start, on a 10-minute retry, and on "Send waiting … now".
- **Without a key** it still reads and stores everything as usual, sends nothing, sets no retry timer, and just notes "N waiting – no GitHub key saved yet".
- **What the gathering step requires:** each record needs `grader`, `cert` (4–14 digits) and `read_at`. It must not have a `file` field, because the gathering step adds that.
- **Duplicates:** opening the same cert twice saves twice on GitHub. Downstream, the newest read wins.

## The three problems and how they were settled

1. **The gathering step only saw 1,000 files**, and its cleanup could wipe unread ones. The other chat fixed this. It now copies the inbox with git (no 1,000 cap, no API calls), removes taken files in one commit, and resets the inbox only via `--force-with-lease` against the exact copy it read. It was tested with 1,001–1,500 files and with files added mid-run.
2. **GitHub allows about 500 content-creating API requests an hour** (80 a minute) per account, and the extension makes one per page.
   - On GitHub, the extension gets **no key**. `11.py` takes the reads from its storage and **git-pushes them in batches of 100**, in the extension's exact file format.
   - Git pushes aren't REST API calls, so the 500/hour limit doesn't apply, and there are no double saves.
3. **Proxy cost:** every page now has to load in a real browser, so there's no plain-text shortcut. The savings:
   - skip pictures, fonts, styles, video and a list of tracker domains (`LIGHT`, after each IP's first page), falling back to a full load if a page gives no read;
   - keep each browser's profile (and so its cache) for the whole run;
   - nothing else goes through the proxy;
   - each run reports roughly how much proxy data each page used.

   **Rough guesses:**
   - Data: 15–50 GB for ~130,000 links, about $40–200 at Decodo's $2–4/GB.
   - Alternative: Decodo dedicated ISP proxies, from about $2.90 per IP per month for 10, listed under "unlimited bandwidth" (the ISP data terms aren't explicit, so confirm with Decodo). They're static addresses, so more risk of Cloudflare blocks.
   - The owner agreed: measure on the first 50 links, then decide.

## How `11.py` works

- **Plan** (standard library only): reads the links file and `opened.csv`, and says whether anything is to do. Done = `saved` or `not found`, or `MAX_TRIES` (3) failures unless *retry failed* is ticked.
- **Checks before any link is opened:** both secrets are set; the extension folder has a `manifest.json`; `git ls-remote` with the key works; the proxy answers (a 407 means a wrong password or a plan out of data). Any failure stops the run with a plain message.
- **Each browser:**
  - Scrapling `AsyncStealthySession` on bundled Chromium (`real_chrome=False`, since branded Chrome no longer accepts `--load-extension`), headful under `xvfb-run`.
  - Loaded with `--disable-extensions-except` / `--load-extension`. Scrapling already strips Playwright's `--disable-extensions`.
  - A fixed `user_data_dir` per browser, which keeps the cache and the extension's storage across restarts.
  - Its proxy is one Decodo port, with the clock set to that IP's time zone.
- **Talking to the extension:**
  - Its ID is computed from the folder's real path (SHA-256 of the path, first 32 hex digits mapped to a–p). This matched the real ID in tests. If it doesn't load, the ID is taken from its service worker instead.
  - The run keeps the extension's popup open in a second tab and uses it to read and write `chrome.storage.local`. With Patchright this needs `evaluate(..., isolated_context=False)`.
  - At start it removes `ghKey` and sets `autoSave` to false.
- **Each link:** `session.fetch(url, page_action=...)`. Scrapling runs `page_action` after its Cloudflare solver.
  - The action polls `records` until there's a read and it hasn't changed for `SETTLE_SECONDS` (5), or until `READ_WAIT_SECONDS` (25) passes with no read.
  - Each read is then removed from the extension's storage, so whatever is in `records` always belongs to the current link, and handed to the saver.
  - Blocks are handled as in `8.py`: a second look at a challenge, then moving to another port (at most twice), with a 10-minute port rest, a pause after 10 blocks in a row, a stop after 3 pauses, and a stop after 6 errors in a row.
- **Saver:**
  - Batches across both browsers: the first save after 5 reads (to catch a bad key early), then every 100, plus at the end of the run.
  - Each save is a fresh shallow clone of the inbox, the files written, one commit, then a push. It retries up to 6 times on a fresh clone, so it copes with the gathering step's resets.
  - Auth errors stop the run with a message about the key.
  - Links become `saved` in `opened.csv` only after their batch is pushed. Reads not saved by the end are marked `not saved` and opened again next run.
- **Privacy:** output only shows row numbers and counts. Links, the links file's hostnames, the proxy password and the key are masked. Nothing from a read is printed.

## Tests (2 Nov 2026, in the sandbox)

**The stand-ins:**
- a fake MV3 extension behaving like the owner's: `records`/`outbox` in storage, a key in the popup, and a send to a fake collector only when a key is set;
- the fake Cloudflare-style site, with a table that appears 2.5 s late, pages that only get their content after a stylesheet loads, a page with nothing to read, and a 404;
- the fake proxy (3 ports, one always blocked);
- a bare-repo inbox, plus a fake gathering step that copies files out and resets the inbox with `--force-with-lease` every 3 s.

**Results:**
- **Normal run:** 11 links read and saved (in saves of 5 and 6). The files were named and formatted like the extension's, and included the late table. The 404 was recorded, and the extension made **zero** sends of its own.
- **Light-mode fallback:** stylesheet-dependent pages came out with no read in light mode, were reopened in full and read. After 3 of those, the run switched to full pages.
- **No loss under resets:** with the fake gathering step resetting the inbox mid-run, all 28 reads from three runs ended up taken or still waiting.
- **Retries and bad keys:** a push turned away once was retried on a fresh clone and went through. A permission error stops the run with the key message.
- **Setup mistakes:** a missing extension folder, missing secrets and a wrong proxy password each stop the run with a plain message before any link is opened.
- **Lint and privacy:** `actionlint` (with shellcheck) passes on `12.yml`, and the logs had no links, hostnames, page text, read values, username, password or key.

**Not tested:** real GitHub Actions, the real extension, real Decodo, and real Cloudflare from GitHub's Linux machines. The first run of 50 links is the real test.

## Run reports (how this chat sees what happened)

The builder chat never opens `results-links`. So every run of `12.yml` posts a comment on **issue #1, "Link opener reports", in this repo**. It holds the run's result, each step's outcome, and the last 40 lines of the opener's log (row numbers, counts and stop reasons only), plus the end of the install log if installing failed.

It needs the optional secret `SCRAP_REPORT_KEY` in `results-links`: a fine-grained key for `BrettS600/scrap` only, with Issues: Read and write. Without it the step just says no report was sent.

When the owner says "check the last run", read issue #1's newest comments.
